# `news_protocol/` — the news-pipeline design authority

The rules, methodologies, pre-registrations and decision records that govern
the news side of the project. This directory answers "why is it done this
way?" — it is the design authority the code in `src/` implements, kept
separate from the code and its outputs so a decision can be read without
reading the program. The final corpus was collected under the protocol
**together with its documented amendments and corrective reruns**; the four
sections below keep the current rules, the machine-readable evidence, the
corrections and the historical records clearly apart.

## 1. Current governing rules

The documents the final corpus and features were actually screened and
sampled under.

| Document | What it fixes |
| --- | --- |
| `article_eligibility_rules.md` | the pre-registered I1–I6 / E1–E10 eligibility rules the report's appendix reproduces |
| `eligibility_manual_review_codebook.md` | the human-review codebook behind the recorded review decisions |
| `division_sample.md`, `division_sample.csv` | the frozen 17-division local search sample (generated by `src/build_division_sample.py`; its commit time anchors the area-selection check in the repository-root leakage audit) |
| `news_source_registry.csv` | the registry of news sources, their coverage reach and access routes |
| `raw_news_schema.md`, `raw_news_schema.json` | the raw-news record schema the collection engine enforces |
| `historical_coverage_audit.csv` | the audited news-coverage-back-to date per source |

## 2. Machine-readable evidence

| File | What it holds |
| --- | --- |
| `evidence/coverage_verification_2026-07-22.json` | the dated source-coverage verification behind the coverage audit |
| `evidence/pilot_records.json` | the records supporting the retrieval-validation pilot |

## 3. Amendments and corrections

| Document | What it records |
| --- | --- |
| `collection_faults_and_corrections.md` | every fault found during collection and what correcting it cost — the honest record of how execution deviated from the first plan (interface substitutions, quoted-query and date-restriction reruns, scope extensions) |

## 4. Historical and superseded development records

Dated records kept for the development trail; each carries a status note at
the top stating what subsequently happened. None of them describes the
current state.

| Document | What it was, and what superseded it |
| --- | --- |
| `news_research_protocol.md` | the original preregistration snapshot; the final collection followed it plus the documented amendments above |
| `eligibility_manual_review_methodology.md` | the review methodology as v2 was being proposed; the frozen v2 classifier was subsequently validated and used |
| `llm_v2_feasibility_plan.md` | the pre-freeze development plan for the v2 classifier |
| `retrieval_validation_report.md` | the pre-collection validation that declared the retrieval framework ready |
| `source_adapter_framework.md` | the adapter design later implemented in `src/news_collection/adapters.py` |
| `news_analysis_scope_decision.md` | the scope decision with execution counts as of 30 July 2026 |
| `feature_selection_findings.md` | findings from the removed ward-level pilot feature chain; its open splitting item was addressed by the Stage 1 split design |

See `REPO_MAP.md` for how the protocol governs the collection, cleaning, LLM
and feature layers.
