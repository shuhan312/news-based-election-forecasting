## 4. Provenance guarantees (spot-checkable)

Every record carries: query ID (joins to one search-log row), adapter + version, access route, requested/final/archive URLs, HTTP status, retrieval status, retrieval timestamp, software and protocol versions, all date candidates with evidence labels, and a SHA-256 of the extracted text. Raw sidecars per article: `html/` (as fetched), `api_raw/` (raw API item), `text/` (extracted text). Records are idempotent by canonical reference, so resuming never duplicates identities; re-running a query appends a new log row rather than editing history.

## 5. Unresolved issues and manual follow-ups (U-series)

* **U1 — Woking News & Mail and Farnham Herald site search harvest zero links.** Both search pages answer HTTP 200 but render results with client-side JavaScript, so static link harvesting finds nothing (24 zero-result searches, all logged). Follow-up: per-site result selectors, their WordPress JSON/RSS endpoints, or the Wayback/manual routes. No robots violation is involved.
* **U2 — Site search cannot reach historic windows.** Publisher search returns current pages regardless of the queried election (visible as cross-election `existing` hits in the log). Expected from the audit: historic local recall belongs to the CDX (D) and manual (M) routes; site search's real value is the 2026 window.
* **U3 — Ward-tier inventory for 2013/2026 blocked on inputs** (see §2). Follow-up: promote the official 2013 division/candidate extraction into `data/elections/`, and run `src/fetch_2026_surrey_results.py`; then regenerate the inventory as v1.1.
* **U4 — Stage C is gated on the committed division sample** (protocol §9 pre-registration; supervisor to-do 7). The runner refuses stage C until `news_protocol/division_sample.md` exists.
* **U5 — Cross-query discovery linkage.** When several queries surface the same article, only the first writes the record; later hits are counted in the log but the per-hit URL linkage is not stored. Acceptable for dedup (text hashes exist) but noted for the feature stage, which may want full query↔article edges.

## 6. Recommendations before downstream processing

1. Deepen stage B (raise per-query caps) and execute stage D with a dedicated budget of several hours of CDX time; both are resumable as-is.
2. Resolve U1 with per-site selectors before relying on site search for 2026 local coverage.
3. Commit the division sample (unblocks stage C, 162 queries) and the 2013/2026 ward tables (unblocks inventory v1.1).
4. Proceed to **Publication Date Resolution** next, as planned: 156 flagged conflicts plus 5.4% missing dates is a well-bounded, auditable workload.
5. Keep NewsAPI dormant unless the supervisor funds an upgrade; nothing downstream depends on it.
6. **Proposal P3 (for supervisor review): automate the Google route via the official Google Programmable Search JSON API.** The manual-only status of `google_dated_search` exists because scraping Google's results pages violates its terms of service; the official Custom Search API has no such problem, supports date restriction and site restriction, and would let the stage-M ward queries run through a `GoogleCseAdapter` inside the existing runner (same inventory, logs and schema). Cost is negligible: 100 free queries/day, or ~US$5 per 1,000 — the sample-reduced ward workload (~400–600 queries after division sampling) fits in the free tier within a week. Pure manual search would remain only as a fallback for anything the API misses.
